# Compatibility policy

The package version is the single release-level compatibility signal and follows [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html).
Users primarily interact with the package and catalog syntax.
The catalog has no independent SemVer or release cycle.
This policy applies to releases after its adoption; it does not retroactively cover interfaces removed earlier.
The existing migration and maintenance boundaries remain documented in [Removed interfaces](removed-interfaces.md).

## Guarantees and current behavior

Compatibility is judged by user reliance, workflow impact, migration cost, and preservation, rather than by whether a detail appears in documentation.
Command and configuration references describe the current release; this policy identifies the guarantees that remain stable within a major version.

The following guarantees are protected:

- **Explicit choices**: Accepted command names, selectors, explicit configuration values, and intentional opt-outs retain their meaning and supported workflows.
- **Data and ownership**: Local edits, excluded entries, credentials, ownership identities, transaction recovery, and publication authorization remain protected.
- **Saved installations**: Machine and state files generated by supported releases remain usable or receive safe conversion; installed callbacks retain a usable invocation.
- **Automation interfaces**: Documented JSON field types and meanings, exit-code conventions, and the distinction between current results and historical observations remain usable by callers.
- **Support requirements**: Removing a supported runtime or operating system requires an incompatible release.

Defaults and restrictions can evolve in a minor release when previously successful workflows still work, explicit choices remain honored, and the change creates no new destructive or external effects.
Assess omitted values as well as explicit ones: reliance on an old default can make a default change incompatible.
A more permissive implementation is not automatically compatible if it can publish more data, weaken conflict checks, or change what an existing installation owns.

Representative classifications follow these criteria:

| Change | Classification and reason |
| --- | --- |
| Faster inspection, clearer human diagnostics, or removal of a redundant validation that preserves accepted results | Patch; no workflow or preservation change. |
| Infer the only connected agent instead of failing for an unconnected default | Minor when existing successful lookups retain their destination. |
| Accept an additional payload type while preserving explicit rejection policies and opaque inspection | Minor only when existing installations and omitted-value reliance remain safe. |
| Change default exclusions so previously included user data disappears from copies | Major; changes delivered contents and requires an inclusion override and migration notice. |
| Gather installed copy edits during ordinary publication | Major; expands the user-authorized data flow of an existing command. |
| Remove native Windows support or invalidate generated configuration | Major; ends a supported workflow or requires migration. |

Internal Python functions, storage layouts, human-readable diagnostic wording, JSON whitespace, and object key order are not stable interfaces.
Their implementation can change while preserving the guarantees in this policy.

JSON consumers must ignore unknown object fields; new fields are compatible when existing meanings remain intact.
New enum values are incompatible unless the interface explicitly allows unknown values and defines their handling.
Unknown input configuration fields remain errors.

Every user-visible default or behavior change needs a changelog notice identifying its effect and any explicit alternative.
Changes requiring migration must include instructions and preservation tests, even in a major release.
[Commands](commands.md) and [Configuration](configuration.md) remain authoritative for the current release's syntax and behavior.

## Final release classification

For final releases from `1.0.0` onward, use PATCH for backward-compatible bug fixes, MINOR for backward-compatible functionality or public deprecation, and MAJOR for incompatible public-contract changes.

### Patch eligibility

PATCH eligibility never relaxes compatibility requirements.
Previously valid calls must retain their success conditions, primary results, configuration compatibility, and ownership and recovery guarantees without user migration.
An ancillary integration reports recoverable failures separately so the existing workflow can complete.
Unsafe shared state and unresolved recovery remain fatal.
Required reconfiguration, new fatal prerequisites for previously valid calls, and incompatible enum values do not qualify.

### Classification rules

Classify a release by its most significant change, based on the previous released contract rather than intermediate development states.
Documentation corrections and internal maintenance that preserve the contract may ship in a PATCH release.
Do not modify an already released version's contents.
A bug-fix label alone does not justify breaking previously valid documented use in a PATCH release.

The following changes require the incompatible-change increment:

- Removing an option.
- Changing a default or selection scope so previously valid use loses its promised behavior.
- Invalidating an existing catalog.
- Breaking an installed callback.
- Dropping a supported runtime.

Document replacements and any required user migration when deprecating or breaking an interface.

## Prereleases and the first stable release

The first final `1.0.0` defines the stable public contract; its prereleases may refine that contract without requiring a `2.0.0` release.

### Prerelease review

Prerelease changes still require compatibility review, preservation of user data and ownership, and documented migration for changed behavior.
Do not replace the contents of an existing release tag or package version.

### Self-update permissions

AEM self-update permissions are distinct from the required final-release version increment.
For prereleases, `compatible` permits only a higher numeric subversion with the same base version and label.
Releases within that series must therefore preserve the previous released contract.

Changing the base version or label, or graduating to final, requires `breaking` permission even when the transition contains no incompatible change.
The permission therefore allows a transition; it does not assert that every such transition breaks compatibility or requires another MAJOR increment.
See [release selection](automation/self-update.md) for supported tag spellings and ordering.

## Configuration and saved-state formats

Catalog, machine, and state format versions are integer interpretation markers, not independently released product versions.

### Version markers

Do not increment them for ordinary compatible additions; change a marker when readers need to distinguish incompatible representations or interpretations.
An unchanged marker does not make an incompatible change compatible.
Changing a marker does not itself require a package MAJOR increment if supported reading or conversion safely preserves the previous contract.

### Responsibility and migration

AEM is responsible for machine and state compatibility.
Users must not have to edit version markers or discard ownership records to upgrade.
Removing support or requiring manual reconfiguration is an incompatible change even when the affected data is generated rather than hand-written.

This policy does not imply automatic migration.
Any future conversion must preserve contents, ownership, and recoverability, and must be documented and tested.
Review compatibility against existing catalogs, saved machine/state data, and installed integrations, using fixtures for the affected released contracts when implementation changes.
